MMedPO inference on the HGX-01 cluster

Runs on the cluster. Memory is not a constraint.

The released MMedPO model (LLaVA-Med v1.5, Mistral-7B, with MMedPO LoRA weights merged in) ran on the full public test sets inside a Slurm batch job on hgx-01. Each run used a single B200 GPU and the authors' own inference settings. One test set, MIMIC-CXR, needs credentialed access, so the MIMIC checkpoint was timed on IU-Xray images instead (see notes).

Model load takes 17 s when one copy loads alone. With four copies loading at once from /home, it took 36–45 s.

Does the setup reproduce the paper?

As a quick check, I scored the closed-ended (yes/no) answers: correct if the reference answer appears in the first three words of the model's reply. This is cruder than the paper's evaluation script, but it lands close to the paper's numbers:

The IU-Xray reports read like real radiology findings and closely match the reference reports, e.g. “normal heart size and mediastinal contours… lungs are clear… no pleural effusion or pneumothorax”.

What was measured

Model
microsoft/llava-med-v1.5-mistral-7b + MMedPO LoRA (r = 128) from zky11235/mmedpo_checkpoints, merged at load time. CLIP ViT-L/14-336 image encoder, 576 image tokens per image.
Settings
As in the authors' scripts: fp16, batch size 1, vicuna_v1 prompt, temperature 0.2 sampling, at most 64 new tokens for VQA and 1,024 for reports.
Hardware
1× NVIDIA B200 (183 GB) on hgx-01, Slurm batch job 266, partition hgx. The four runs used four different GPUs at the same time.
Software
PyTorch 2.8.0 + CUDA 12.8, transformers 4.37.2, peft 0.11.1, Python 3.10.
Test sets
VQA-RAD test (451 QA), SLAKE English test (1,061 QA), IU-Xray test (590 studies, first view), all from public Hugging Face copies. The counts match the paper's Table 6.

Notes and caveats

  • EnvThe paper's environment (PyTorch 2.1.2) cannot run on B200 GPUs, which need sm_100 kernels. PyTorch 2.8 works, and the authors' model code ran without changes.
  • SlurmSlurm on this cluster does not allocate GPUs (no GRES), so every job sees all 8 B200s. The job scripts pick an idle GPU themselves. Another user's job on the same GPU would slow these timings down; all 8 GPUs were idle during this run.
  • DataMIMIC-CXR needs PhysioNet credentialed access, so the MIMIC checkpoint was timed on IU-Xray chest X-rays. That gives its compute cost, not its report quality. On these out-of-domain images it sometimes repeats itself: 7 of 590 reports ran to the 1,024-token cap, about 11 s each.
  • CostMMedPO changes only the weights. The LoRA is merged in, so the network has the same size and per-token cost as plain LLaVA-Med v1.5. Only the answer length can differ. (This follows from the architecture; I did not time the base model separately.)
  • HeadroomAt batch size 1, generation runs at about 8–10 ms per token. That speed is limited by Python and per-token kernel-launch overhead, not by the GPU, which stays mostly idle. The authors' script already spreads a test set across GPUs with torchrun, which should cut the whole-set times roughly in proportion to the number of GPUs. I have not measured that.
  • TrainingNot measured. The paper reports 2–3 hours on 4× RTX A6000 (48 GB) for LoRA preference training. Each B200 has almost 4× the memory of an A6000.

Reproduce

Everything lives in ~/MRI-MMedPO on the cluster: the environment, weights, test sets, scripts, logs, and every per-sample answer with its timings.

sbatch ~/MRI-MMedPO/scripts/setup_env.sbatch   # env + weights + test sets (CPU only)
sbatch ~/MRI-MMedPO/scripts/run_bench.sbatch   # 4 timed runs, one idle B200 each
~/MRI-MMedPO/.venv/bin/python ~/MRI-MMedPO/scripts/summarize.py
